# Deal Trajectory Engine

A four-phase GTM engineering system that detects stalling deals before reps notice, identifies where stated loss reasons contradict behavioral evidence, and generates prioritized, rep-specific intervention cards.

**🔗 Live dashboard:** [deal-trajectory-engine.vercel.app](https://deal-trajectory-engine.vercel.app/)

---

## What it does

Standard pipeline tools surface that a deal is dying after it's already dead. This system works backward from historical win/loss patterns to detect behavioral drift in active deals — specifically which of four stall signatures is present, how severe it is, how much of the intervention window remains, and exactly what to do about it.

The output is not a dashboard. It's a prioritized action queue with a specific first move per deal, grounded in what actually worked in comparable historical deals.

## Architecture

```
Phase 1: Data Generation
  generate_mock_data_v2.py
  └── historical_deals.csv      (1,030 rows, 97 fields)
  └── active_pipeline.csv       (150 rows, 97 fields)
  └── data_metadata.json

Phase 2: Win/Loss Synthesizer
  synthesizer.py
  └── stall_signature_library.json   (data-derived thresholds)
  └── win_loss_patterns.json         (signal stats, effect sizes)
  └── feature_importance.json        (GBM permutation importance)
  └── contradiction_report.csv       (28.1% of losses misattributed)
  └── intervention_library.json      (recovery playbook per stall type)
  └── synthesis_report.md            (LLM narrative summary)

Phase 3: Stall Predictor
  stall_predictor.py
  └── scored_pipeline.csv            (all 150 deals with scores)
  └── flagged_deals.csv              (74 at-risk + critical deals)
  └── intervention_queue.json        (priority-sorted action cards)
  └── predictor_summary.json         (aggregate stats)

Phase 4: Intervention Card Generator
  intervention_card_generator.py
  └── manager_brief.md               (daily ops brief, top 10 actions)
  └── dashboard_payload.json         (full serialized output for UI)
  └── dashboard.html                 (self-contained browser dashboard — opens by double-clicking)
  └── cards/                         (individual markdown cards, top 20)
```

## Running it

Run phases in order. Each phase reads from the previous phase's outputs.

```bash
# Phase 1 — generate mock data
python generate_mock_data_v2.py

# Phase 2 — win/loss synthesizer
python synthesizer.py

# Phase 3 — stall predictor
python stall_predictor.py

# Phase 4 — intervention card generator
python intervention_card_generator.py
```

Total runtime: approximately 60–90 seconds for all four phases. Phase 2 is the longest due to the GBM training and permutation importance calculation.

## About the data

**All data is synthetic.** Generated by `generate_mock_data_v2.py` using Faker and NumPy with a fixed random seed (42) for reproducibility.

### Deliberate imperfections

The mock data is intentionally messy to stress-test the system. Issues include:

- ~3% duplicate deal IDs (suffixed `-DUP`) — the cleaning step in each phase drops these
- Mixed date formats within the same column (`YYYY-MM-DD`, `MM/DD/YYYY`, `DD-Mon-YYYY`, `Month DD, YYYY`)
- Inconsistent company name formatting (`Acme Corp`, `ACME CORP`, `Acme Corp, Inc.`, `The Acme Corp`)
- Random nulls at realistic rates: ~8% on most behavioral fields, ~22% on `sdr_name`, ~30% on `budget_range_stated`
- **Intentional contradiction layer:** ~45% of lost deals have a `stated_loss_reason` that doesn't match the `injected_stall_signature` — the ground truth label. This is the "lie detector" the Win/Loss Synthesizer is designed to catch.

### Key fields for validation

| Field | Notes |
|-------|-------|
| `injected_stall_signature` | Ground truth label — which stall pattern was artificially injected into behavioral fields. `NULL` = healthy or won deal. **Use for validation only, not as a model input.** |
| `stated_loss_reason` | What the rep logged. Intentionally contradicts `injected_stall_signature` ~45% of the time. |
| `outcome` | Won / Lost. Historical deals only — active pipeline has no outcome. |
| `email_response_latency_delta_days` | Change in email response time from start to end of deal. Positive = slowing down. |
| `champion_engagement_score_delta` | Change in champion engagement score over the cycle. Negative = disengaging. |

### Generating fresh data

Re-running `generate_mock_data_v2.py` produces a new dataset with different company names, rep names, and deal IDs but the same statistical distributions (seeded). To change distributions, edit the `STALL_SIGNAL_AFFINITY` dict and the injected signal overrides in `build_deal()`.

## Stall signatures

Four patterns derived from the historical data, not hardcoded assumptions. Thresholds are set at the midpoint between the median of stalled deals and healthy won deals for each defining signal.

| Signature | Description | Top signals |
|-----------|-------------|-------------|
| Champion Collapse | Champion disengages or loses authority mid-cycle | email_response_latency_delta, champion_engagement_score_delta, unique_stakeholders_at_midpoint |
| Competitor Displacement | Competitor gains foothold via pricing pressure + stage regression | competitive_mentions_count, discount_pct, stage_regression_count |
| Ghost Stall | Prospect goes silent with no stated reason | days_since_last_rep_touch, days_in_current_stage, meeting_count_last_30d |
| Exec Vacuum | Deal confined to IC champion with no economic buyer visibility | executive_sponsor_engaged, economic_buyer_meetings |

---

## Scoring logic

Each active deal is scored against all four signatures. The score (0–1) represents the fraction of defining signals breached. Key design decisions:

**Urgency weighting:** The same signal at 80% of a deal's expected cycle gets a 1.3× multiplier vs 0.8× at 20%. A Ghost Stall in Negotiation is more urgent than the same pattern in Discovery.

**Stage gating:** Stall signatures are suppressed in stages where they aren't meaningful. Exec Vacuum doesn't fire on Prospecting or Discovery deals — a rep not having exec access at day 3 is normal, not a stall signal.

**Minimum signal gate:** A deal must breach at least 2 defining signals to be tagged at-risk or critical. Single-signal hits are watch-level at most.

**Priority scoring:** `stall_severity × log(ACV) × urgency_multiplier`. Highest ACV + latest stage + strongest stall pattern = top of queue.

---

## Model performance

The Win/Loss Synthesizer trains a Gradient Boosting classifier on 29 behavioral signals.

- Cross-validated AUC: **0.841 ± 0.034** (5-fold)
- Top predictive signals: `days_since_last_activity`, `executive_sponsor_engaged`, `competitive_mentions_count`, `champion_engagement_score`, `email_response_latency_delta_days`

The Stall Predictor's stall type classification achieves **69.5% accuracy** against ground truth labels on the active pipeline, using only behavioral signals (no access to `injected_stall_signature`).

## Known limitations and explicit punts

**No feedback loop.** Every intervention generated should be logged, outcomes should feed back into the pattern library, and thresholds should tighten over time. This is the most important missing piece. The architecture is described in the writeup; building it was punted due to time budget.

**Global thresholds.** Stall signature thresholds are derived from global medians across all segments. In production you'd want per-segment, per-industry thresholds — Champion Collapse in Enterprise looks different from SMB.

**No CRM connectors.** Everything runs on CSV. Real deployment requires Salesforce/HubSpot API integrations and a scheduler.

**LLM call volume at scale.** Phase 4 makes one API call per flagged deal. At 1,000 active deals with 60% flagged, that's 600 calls per run. Production would need batching and caching on deal fingerprint hash, regenerating only when signals change materially.

**Multi-signature deduplication.** A deal can satisfy two stall signatures simultaneously. The system surfaces the dominant one by weighted score, but a production system would need a sequencing layer to handle compound stalls (e.g., a deal that's both in Ghost Stall and Exec Vacuum simultaneously needs a different intervention than either pattern alone).
